# Notas de la Versión - v0.3.0

**Fecha:** Marzo 2026
**Enfoque:** Optimización de consultas, enriquecimiento de investigadores con CvLAC y homologación de categorías de revistas.

## 🚀 Nuevas Características

### Endpoint `GET /api/groups/` enriquecido
* El endpoint de listado de grupos ahora incluye conteos de producción académica por grupo, calculados mediante anotaciones en la consulta ORM (sin consultas adicionales por grupo).
* Nuevos campos en la respuesta:
  * `leader` — nombre del líder del grupo (campo directo del modelo `ResearchGroup`).
  * `articles_count` — total de artículos asociados al grupo.
  * `books_count` — total de libros asociados al grupo.
  * `chapters_count` — total de capítulos de libros asociados al grupo.
  * `theses_count` — total de tesis asociadas al grupo.
  * `researchers_count` — total de miembros activos e inactivos del grupo.

### Enriquecimiento de Investigadores con Fallback CvLAC (`enrich_researchers`)
* El comando `enrich_researchers` implementa ahora un proceso de dos etapas:
  * **Etapa 1 — datos.gov.co (fuente primaria):** Consulta batch a la API Socrata del Ministerio de Ciencia para obtener la categoría MinCiencias más reciente de cada investigador. Las cadenas completas (ej. `"Investigador Senior"`) se normalizan a nombres cortos (`Senior`, `Asociado`, `Junior`, `Emérito`).
  * **Etapa 2 — CvLAC (fallback histórico):** Para los investigadores sin categoría asignada en la etapa 1, se realiza una solicitud HTTP a su perfil CvLAC (`cvlac_url`) y se extrae la categoría mediante scraping con BeautifulSoup. Se respeta un delay de 300ms entre solicitudes para no sobrecargar el servidor del MinCiencias.

### Homologación de Categorías Scimago → Publindex (`enrich_articles`)
* El comando `enrich_articles` aplica la siguiente tabla de equivalencias al guardar la categoría de cada artículo de revista indexado en Scimago:
  * `Q1` → `A1`
  * `Q2` → `A2`
  * `Q3` → `B`
  * `Q4` → `C`
* Las revistas ya clasificadas por Publindex con letras (`A1`, `A2`, `B`, `C`) pasan sin cambio. Esto unifica la escala de presentación en el front-end.

## ⚡ Optimizaciones de Rendimiento

### Consultas correlacionadas en `views.py`
* La vista `get_groups_list` reemplazó cinco `COUNT DISTINCT` con JOINs por subconsultas correlacionadas (`Subquery` + `OuterRef`). Esto eliminó el problema de filas cartesianas que provocaba tiempos de respuesta colgantes. La latencia bajó de >30s (timeout) a ~23ms.

## 🔄 Detalles Técnicos

* Se utilizan subconsultas correlacionadas (`Coalesce(Subquery(..., Count('id')), 0)`) con las `related_names` del modelo:
  * `articles` → `Article.group`
  * `books` → `Book.group`
  * `chapters` → `BookChapter.group`
  * `theses` → `Thesis.group`
  * `members` → `GroupMember.group`
* La consulta ORM se traduce en N subconsultas `SELECT COUNT(*)` correlacionadas, que PostgreSQL optimiza como **index nested loops** sobre las FK indexadas.
* Retrocompatible: los campos anteriores (`id`, `name`, `code`, `category`) no fueron modificados.
